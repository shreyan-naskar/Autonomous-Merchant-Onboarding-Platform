# Sample payloads

JSON bodies for `POST /applications`. From the repo root:

```sh
curl -X POST localhost:3000/applications -H 'content-type: application/json' -d @sample-data/happy.json
```

Each file uses its own PAN, GSTIN and bank account, so they don't collide with
each other (relevant once duplicate detection exists). In every file the GSTIN
embeds the PAN (characters 3-12), as a real GSTIN does.

| File | What is special | Trigger | Expected path |
|---|---|---|---|
| `happy.json` | nothing | all values consistent, no magic values | extraction OK -> `VERIFYING` -> `VERIFIED` -> `APPROVED` -> `MERCHANT_CREATED` |
| `gst-fail.json` | GSTIN `29AACCM5678P1Z9` | **GST ending `Z9`**: the mock GST provider fails it | PAN passes, GST fails -> `IN_REVIEW` (`PAN_OK_GST_FAILED`) |
| `conflict.json` | PAN card name `Ramesh Electricals Pvt Ltd` vs form `Ganesh Hardware Stores` | document name differs from form name | `IN_REVIEW` with review task `DOC_CONFLICT` |
| `missing.json` | no `GST_CERT` document | required document missing | `NEEDS_INFO`, missing items listed in the audit detail |
| `high-risk.json` | merchant name `Risky Ventures Pvt Ltd` | **name containing `RISKY`**: risk score 85 | all checks pass -> `VERIFIED` -> `IN_REVIEW` (`HIGH_RISK`); operator approve -> `MERCHANT_CREATED` |
| `low-confidence.json` | bank proof IFSC `KKBK2002468` (form: `KKBK0002468`) | document value is not a valid IFSC: confidence 0.5 | `IN_REVIEW` with review task `LOW_CONFIDENCE` |

## Document files (Phase 7)

`missing-gst-cert.pdf` is the GST certificate that `missing.json` lacks:
submit `missing.json`, then upload this file in the "Information needed from
the merchant" panel to complete the application.

`pan-sharp.png` and `pan-blurry.png` are a synthetic PAN card (marked "SAMPLE
DOCUMENT - NOT VALID") for `ocr-pan.json`'s merchant, generated by
`npx tsx scripts/generate-sample-images.mts`. `ocr-pan.json` has the form and
the GST/bank documents but no `PAN_CARD`: upload one of the images as the PAN
card (multipart, or the file input on the Submit application page).

```sh
curl -X POST localhost:3000/applications \
  -F merchant_name='Sunrise Traders Pvt Ltd' -F pan=AAFCS4321M -F gst=27AAFCS4321M1Z5 \
  -F bank_account=60200987654321 -F ifsc=ICIC0004321 \
  -F "documents=$(node -p 'JSON.stringify(require(\"./sample-data/ocr-pan.json\").documents)')" \
  -F PAN_CARD=@sample-data/pan-sharp.png
```

| Upload | Blur score (threshold `BLUR_THRESHOLD`, default 30) | Expected path |
|---|---|---|
| `pan-sharp.png` | ~990 | OCR reads PAN + name (confidence ~0.94) -> `VERIFYING` -> ... -> `MERCHANT_CREATED` |
| `pan-blurry.png` | ~1.7 | no OCR -> `IN_REVIEW` with review task `BLURRY_DOCUMENT` |
| `pan-sharp.png` with a different form PAN | ~990 | `IN_REVIEW` `DOC_CONFLICT` (OCR PAN differs from form) |

`gst-cert.pdf` and `bank-proof.pdf` (same merchant, same generator) have a
real text layer: upload them as `GST_CERT` / `BANK_PROOF` (`-F GST_CERT=@sample-data/gst-cert.pdf
-F BANK_PROOF=@sample-data/bank-proof.pdf`, dropping the `documents` field) and
their text layer (read with pdfjs, rows rebuilt by position) gives the same fields as the JSON documents, at
confidence 0.95. When the text layer is missing or lacks fields (a scan, or a scan
under a typed header), the pages are rendered and OCR'd for the missing fields; text
layer values win. A blurry scan is `IN_REVIEW` `BLURRY_DOCUMENT` like a blurry photo,
and a blank PDF is unreadable (`IN_REVIEW` `LOW_CONFIDENCE`).

OCR and PDF reading run in the worker's `extract` job. The first image downloads the
tesseract English model (~10 MB) into `OCR_CACHE_DIR` (`api/.ocr-cache/`).

Other magic values understood by the mock providers (not used by a file here,
set them in a copy of `happy.json` to try them):

| Value | Effect |
|---|---|
| PAN `ZZZZZ9999Z` (GSTIN must then embed it, e.g. `27ZZZZZ9999Z1Z5`) | PAN verification fails |
| Bank account ending `0000` | bank provider never calls back: the API times out, retries twice, then `IN_REVIEW` (`BANK_TIMEOUT`) |
| Merchant name containing `RISKY` | risk score 85 (above the 70 threshold); other names score 0-40 |

Global chaos settings of the mock providers (affect requests made after the change):

```sh
curl localhost:4000/admin/config
curl -X POST localhost:4000/admin/config -H 'content-type: application/json' \
  -d '{"delayMs":1500,"failKinds":["GST"],"duplicateCallback":true,"dropCallback":false,"lateCallbackMs":0}'
curl -X POST localhost:4000/admin/reset
```

`lateCallbackMs > 0` sends callbacks after that delay instead of `delayMs`
(set it above the API's 30s demo timeout to see a late callback).

The API's in-process worker runs extraction (Phase 3): `happy.json` and
`gst-fail.json` reach `VERIFYING`, `conflict.json` lands in `IN_REVIEW`,
`missing.json` in `NEEDS_INFO`. Paths beyond `VERIFYING` need the mock
providers (Phase 4).

To complete `missing.json`, PATCH the missing document (documents are only
accepted while the application is in `NEEDS_INFO`):

```sh
curl -X PATCH localhost:3000/applications/<id> -H 'content-type: application/json' \
  -d '{"documents":[{"type":"GST_CERT","payload":{"gstin":"33AAECS3456R1Z1","legal_name":"Sunrise Bakery"}}]}'
```

It moves `NEEDS_INFO -> EXTRACTING`, is re-extracted, and reaches `VERIFYING`.

## Specimens (`specimens/`)

Generic test documents for trying uploads by hand, written by
`npx tsx scripts/generate-specimens.mts`. The layout is this project's own
(no emblem, seal, issuer name or official card layout); every file carries a
diagonal "SPECIMEN · TEST DATA · NOT A VALID DOCUMENT" watermark and a footer
with the same text. All values are fictional and belong to one merchant that
passes every provider check:

| Field | Value |
|---|---|
| Business name | Kaveri Looms Pvt Ltd |
| PAN | `AAKCK5678L` |
| GSTIN | `29AAKCK5678L1Z4` |
| Bank account | `30210987654321` |
| IFSC | `KKBK0008521` |

| File | What it is | Outcome (with the GST and bank specimens) |
|---|---|---|
| `pan-specimen.png` | Sharp card image | PAN and name read at or above the 0.8 threshold -> `VERIFYING` |
| `pan-specimen-tilted.jpg` | The same card photographed about 7° off | Straightened, same reading -> `VERIFYING` |
| `pan-specimen-blurry.png` | The card, blurred | `IN_REVIEW` `BLURRY_DOCUMENT` |
| `pan-specimen-name-mismatch.png` | The card in another name (Megha Trading Co) | `IN_REVIEW` `DOC_CONFLICT` (name) |
| `gst-specimen.pdf` | GST registration record with a text layer | Read from the text layer at 0.95 |
| `gst-specimen-scanned.pdf` | The same record as an image-only page | Rendered and read by OCR |
| `bank-specimen.pdf` | Bank account confirmation with a text layer | Read from the text layer at 0.95 |

The magic values above apply as usual: to see a provider failure, type a
GSTIN ending in `Z9` or a bank account ending in `0000` into the form
instead. `api/src/specimens.flow.test.ts` asserts every outcome in this table
with real Tesseract.

## Multipart

The same fields as form parts; files go in parts named after their document
type (`PAN_CARD`, `GST_CERT`, `BANK_PROOF`; PDF, PNG, JPEG, WebP or TIFF, max 5 MB).
Structured documents can be sent alongside as a JSON `documents` part.

```sh
curl -X POST localhost:3000/applications \
  -F merchant_name='Lakshmi Textiles Pvt Ltd' -F pan=AABCL1234K -F gst=27AABCL1234K1Z5 \
  -F bank_account=50100234567891 -F ifsc=HDFC0001234 \
  -F PAN_CARD=@/path/to/pan.pdf
```
